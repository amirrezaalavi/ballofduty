# Playtest — CP4c combat + 4 bots

- **Date:** 2026-10-29
- **Build:** `6caaa4a`, web gzip 11,334 KB, server `:9180`, web `:8099`
- **Tester:** user (Firefox + Chromium), 4 bots
- **Verdict:** **blocked on connection, not on combat code.** The browser never reached the game
  server; everything the user saw happened before/without authoritative combat.

> **Update, same day:** forwarding `9180` as well as `8099` fixed it. Bots now chase, fight, kill
> and respawn; combat is "good and intensive". Remaining feedback: bullets are hard to track, walk
> and sprint should be 5 %/10 % faster, and projectiles 10 % slower. These are folded into
> `docs/PLAN.md` Phase 0.

## The decisive evidence

| Source | Observation |
|---|---|
| `.cache/server.log` | Server started 19:16:59, still listening. Contains **zero `net connect`, `net join`, `net leave`** lines. No roster entry `id=5` while the user played. |
| `.cache/web.log` | `20:33:03 GET /?join=1&port=9180&name=You` (Firefox), `20:34:22 …&name=chrome` (Chromium). Both from `127.0.0.1`. |
| Fresh Playwright join, 20:57 | Connected immediately (`net connect`, `id=5`), got killed by a bot, respawned at full HP. The same server/build works. |

A client that joins this server produces a `net connect` line and an `id=5` row every 30 ticks.
Neither exists for the user's session. So **no input, fire intent, snapshot, or bot attack ever
crossed the socket** for those tabs. The game was effectively offline (or a stale tab), which is why
shots did nothing and bots were inert.

### Most likely cause

The page is opened through a tunnel/forward that exposes **8099 only**. `?join=1` derives the
WebSocket host from `window.location.hostname`, so `127.0.0.1` is used for `ws://…:9180`, which is
the tester's machine (or a closed tunnel port), not this host. Chromium's
`ERR_CONNECTION_REFUSED` and Firefox's "can't establish a connection" match that exactly. Earlier
LAN tests used `192.168.4.120`, which is why they worked.

This is also a product bug: the client gives no visible failure, keeps `net_mode = CLIENT`, and
turns local projectiles off, so the game looks playable while doing nothing.

## Findings

### F1 — Blocker: connection failure is silent (P0)

- `client_start()` sets `net_mode = CLIENT` and `weapon.spawn_projectiles = false` immediately.
- If the socket never opens, the client stays in CLIENT limbo: no bots, no damage, cosmetic tracers.
- The only hint is the small bottom-right `connecting to …` label; nothing in the HUD.
- There is no timeout, no retry, no "disconnected" state, and stale remote ghosts are only cleared
  if a disconnect event fires.
- **Fix direction:** explicit `CONNECTING → CONNECTED → FAILED/TIMEOUT/LOST` state, big HUD banner,
  retry button, `OFFLINE — not connected` mode that restores local play, remove ghosts on loss.
- **Also:** expose one origin (static + WS on the same port via a small reverse proxy) so only one
  port ever needs forwarding.

### F2 — Gun follows the camera 1:1 (P1, design)

`CharacterVisual._update_gun_attachment()` orients the gun socket from `pc.view_yaw` and
`camera_rig.rotation.x`, and `_setup_overlays()` always plays `Pistol_Aim_Neutral`. The gun is
attached to `DEF-hand.R` but its orientation is camera-driven, so it swings with the view.

**Wanted:** gun stays in the hand and follows the character's body/arm; body yaw turns toward the
view when firing (turn-then-shoot); legs keep facing the movement direction; only a short
fire-time alignment, not permanent camera lock.

### F3 — Character and gun fidelity (P1, art)

- Character: Quaternius UAL mannequin (`animation_library.glb`). Clip list has **no strafe clips**
  (only Walk/Jog/Sprint forward, Pistol_Aim_Up/Neutral/Down), so "legs face movement while torso
  faces aim" cannot be done with clips alone.
- Gun: literally a `BoxMesh` `0.05 × 0.07 × 0.30` with a dark material.
- **Needs:** low-poly rifle + hands/arms that read at 2.3 m camera distance, a rig with strafe
  locomotion (or procedural lower-body yaw), and a muzzle/grip socket contract that survives asset
  swaps.

### F4 — Tracer duration / feedback (P2)

- `Tracer` is a 0.9 m box with `_life = 0.08 s`; it vanishes almost immediately and reads as
  "bullets hide quickly". The old CP3 projectile was visible for its flight.
- No impact effect on the client for remote shots; impact spheres are allocated per hit.
- **Fix direction:** 0.15–0.25 s tapered tracer + muzzle flash light, pooled meshes/materials;
  optional visible server projectile for slow projectiles; impact puff and hit spark.

### F5 — Perf hitch on first shots (P2, Firefox-first)

Firefox froze ~2 s around shooting. Candidates: first-use shader compile for the tracer/impact
material, per-shot `BoxMesh`/`StandardMaterial3D` creation, and AudioContext resume on the first
gesture. Chromium was smooth. Pooling and pre-warming the materials should remove the hitch even
before the Firefox-specific work.

### F6 — No combat telemetry (P2)

Server logs deaths and periodic stats, but not shots accepted/rejected, hits, misses, projectile
despawns, or event sizes. Without that, "my shots don't hit" is undiagnosable from a log.

## Firefox issues (postponed by request — recorded)

1. `The WebAssembly exception handling 'try' instruction is deprecated… recompile to use 'try_table'`
   — Emscripten 4.0.20 / Godot 4.7.2 export warning. Harmless today; track for the next Godot.
2. `WebGL warning: drawElementsInstanced: Depth texture comparison requests (LINEAR) Filtering…`
   — shadow/depth sampler filtering; likely engine-side under Compatibility.
3. `WebGL warning: Drawing without vertex attrib 0 array enabled…` — expensive emulation on
   desktop GL; check mesh/format paths.
4. `WebGL warning: drawArraysInstanced: Drawing to a destination rect smaller than the viewport` —
   canvas/viewport sizing under device pixel ratio.
5. `Security Error: … may not load or link to file:///` during reload — transient; verify no
   `file://` resource is referenced from the PCK/HTML.
6. `AudioContext was prevented from starting automatically` — expected until a gesture; resume audio
   on the first click and show a "click to enable sound" hint.
7. `Firefox can't establish a connection to ws://127.0.0.1:9180/` + "connection interrupted while
   the page was loading" — same host/port issue as F1, not a Firefox bug.
8. Background tabs throttle to ~1 FPS in Firefox; two-player tests need two windows/profiles.

## What already works (verified after the report)

- 4 bots spawn, chase, strafe, fire, kill and respawn on the server.
- A joining web client receives snapshots, can be killed, sees `RESPAWNING`, and respawns at full HP.
- Server CPU ~10 % of one core with 4 bots; snapshot 116 B at 5 players.
- 47 automated cases pass; server-authoritative damage, protection, and respawn are covered.
